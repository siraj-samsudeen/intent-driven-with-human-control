# CLAUDE.md

@AGENTS.md

This file adapts the intent-driven template (built for OpenCode) to Claude Code. It moves none
of the template's files:

- `.claude/skills/` links to the template's skills in `.agents/skills/` and `.opencode/skills/`;
  the `openspec-*` skills and `/opsx:*` commands are generated by `openspec init --tools claude`.
  `adversarial-authoring` is the exception: a Claude Code version of the OpenCode skill.
- `.claude/agents/` holds Claude Code versions of the template's `.opencode/agent/` subagents.

## Modes — chosen per change, when it is created

| Mode | Who it is for | Create it with | Schema |
|---|---|---|---|
| **Autopilot** | Work the human wants done, not followed step by step | `openspec new change <name> --schema intent-driven` | `intent-driven` (upstream) |
| **Build** (default) | A maintainer who wants control with few stops | `openspec new change <name>` | `intent-driven-with-human-control` |
| **Learning** | A student or newcomer who learns from every command | `openspec new change <name>` | `intent-driven-with-human-control` |

- **Autopilot** is the upstream flow. The human reviews the planning artifacts (grill-me still
  applies); specs carry fenced Gherkin and tasks are acceptance-test first (`spec-as-source`);
  apply hands acceptance tests to the `senior-qa` subagent and src work to `senior-dev`, and
  several changes may run in parallel worktrees (`openspec-bulk-apply-change`).
- **Build** follows the `outside-in-tdd` skill: one commit per planning artifact, then one stop
  per test for the human's prediction, with red, green and refactor as separate commits. The
  work stays in the main session.
- **Learning** is build mode plus a stop before every command: show it, explain it, wait for
  "run", interpret the result (`outside-in-tdd` § Learning mode).

The human names the mode when asking for the change ("new change add-login, learning mode").
If they do not, use build and say so in the same message as the first draft, so they can switch.
For the `openspec-new-change` and `openspec-propose` skills, "autopilot" counts as the human
naming the `intent-driven` schema, so pass `--schema intent-driven`.
The mode is recorded twice, so any agent resuming the change knows it: the schema in the change's
`.openspec.yaml` (`openspec status --change <name>` prints it) and the first line of
`proposal.md` (`**Mode:** autopilot | build | learning`). Mode-specific lines in
`openspec/config.yaml` say which mode they apply to.

To change a change's mode later: between build and learning, edit the `**Mode:**` line; to or
from autopilot, also change `schema:` in its `.openspec.yaml` and redo `tasks.md`, since the two
schemas plan tasks differently.

## Human control — build and learning modes

Every change — planning artifacts, code, tests, dependencies, config — follows the
`outside-in-tdd` skill: each step is its own commit, and the agent stops only when the human has
something to decide (a draft to review, a real decision, a prediction).

## Defaults — never ask

Formatting and tooling choices are not questions for the human:

- Diagrams: Mermaid, lightweight C4-inspired.
- ADRs: MADR minimal (`.agents/skills/architectural-decision-records/preferences.md`).
- Acceptance-test stack: javascript (`stack:` in `openspec/config.yaml`).

## Continuing — overrides the `openspec-*` skills

When an `openspec-*` skill ends a step by asking whether to continue ("STOP and wait for user
direction", "Ready to create the first artifact?", "Want to continue?"), the `outside-in-tdd` stop
rule wins: continue to the next artifact without asking. Those skills are generated by
`openspec init`/`update`, so this override lives here rather than in them.

## Git — `openspec-git-discipline`, in every mode

The upstream rule applies: every change reaches `main` in two PRs, so a proposal in progress is
visible on `main` before anyone builds it.

1. **Proposal PR** — the planning artifacts (proposal, specs, design, adr, tasks) on a branch,
   merged to `main` before apply starts.
2. **Implementation PR** — the code, tests and `tasks.md` ticks, on a new branch from `main`.
3. **Archive** — on `main`, after the implementation PR merges (sync the specs, then archive).

Differences from the skill, which asks before every commit, branch and PR:

- Approving a step is the user asking for its commit — do not ask again.
- When the last planning artifact (or the reconcile) is approved, push the branch and open its
  PR without asking. Merging is the human's.
- Merge with merge commits, never squash, so the red/green/refactor steps survive.
- Working directly on `main` is fine for a single person; the two phases then become two runs of
  commits on `main` instead of two PRs.

## Reviews and adversarial authoring

See `AGENTS.md` § Review guidelines. On Claude Code, `adversarial-authoring` uses the Codex CLI
as the reviewer when it is installed, otherwise a different Claude model than the author — and
runs only when the human agrees to it.
